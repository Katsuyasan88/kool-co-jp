### 8.1 静的HTMLとSPAルートのパス重複

今回の配置で、静的ファイルとSPAルートのパスが新たに重複した。**工程2の範囲では何も対処していない**が、production公開前に配信側の挙動確認が必要と考える。

- 新規配置した`public/privacy/index.html`と`public/gachacho/terms/index.html`は、buildにより`dist/privacy/index.html`および`dist/gachacho/terms/index.html`として出力される。
- 一方、`src/App.tsx`には同一パスのSPAルートが既存で存在する。
  - `<Route path="/privacy" element={<Privacy />} />`
  - `<Route path="/gachacho/terms" element={<GachachoTerms />} />`
- `deploy.ps1`のstep 3（`aws s3 sync "$Dist/" ... --exclude "assets/*" --exclude "index.html" --exclude "gachacho/legal/*" --delete`）により、これらのHTMLはS3の`privacy/index.html` / `gachacho/terms/index.html`として配置される。
- したがってproduction公開時、`/privacy`および`/gachacho/terms`がSPAルートと静的HTMLのどちらで応答するかは、CloudFrontのカスタムエラーレスポンス（SPAフォールバック）とS3オリジンの設定に依存する。公開前に意図した側が配信されることを確認したい。
- なお`gachacho/legal/*`はstep 4で`Content-Type: application/json; charset=utf-8`を明示して個別配布されるため、`current.json` / `versions/1.2.json`の配信条件は従来どおりで問題ない。

### 8.2 改行コード（`.gitattributes`の適用範囲）

- 既存の`.gitattributes`には次の1行のみが定義されている。

  ```
  public/gachacho/legal/**/*.json text eol=lf
  ```

- 本リポジトリの`core.autocrlf`は`true`。法務JSONは上記ルールにより`eol=lf`が明示され、checkout時もLFのままとなる（`current.json` / `versions/1.2.json`はいずれもCR=0、blobと作業ツリーがバイト一致）。
- 一方、今回新規追加した**HTML 2件は`.gitattributes`の対象外**で、`core.autocrlf=true`が適用される。stage時にgitが次の警告を出した。

  ```
  warning: in the working copy of 'public/gachacho/terms/index.html', LF will be replaced by CRLF the next time Git touches it
  warning: in the working copy of 'public/privacy/index.html', LF will be replaced by CRLF the next time Git touches it
  ```

- 現時点の作業ツリーはLF（CR=0）でCapCole側とバイト一致しており、本記録のSHA-256・buildもこの状態で取得している。commit対象のblobもLFで、作業ツリーとバイト一致することを確認済み。
- ただし**別のWindows環境でclone / 再checkoutすると、この2件はCRLFで展開され、CapCole側とバイト一致しなくなる**（法務JSONについて`.gitattributes`が既に解決している問題と同種）。その状態からdeployすると、配信されるHTMLのバイト列とhashが本記録の値と異なる。
- 対処（`.gitattributes`への`public/**/*.html text eol=lf`等の追加）は**今回の承認範囲外のため実施していない**。production公開前にCapCole側の判断を仰ぎたい。
